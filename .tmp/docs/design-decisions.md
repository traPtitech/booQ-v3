# 設計上の決定事項

ユーザーの回答と追加回答を反映した、今回の概念説明用モックの方針。元の回答は末尾に保存する。内容が異なる場合は以下の決定表を優先する。

| ID | 決定 | モックへの反映 |
| --- | --- | --- |
| D01 | Transaction は貸出のみ | 所有権の変更は UpdateOwnership が担当する。UpdateItem という先の回答は訂正済み |
| D02 | TransactionRequest を分離する | 申請と成立した貸出を別モデルにする |
| D03 | 同条件の物品を数量でまとめる | Quantity は貸出中を含む所有総数。個体管理の別モックは今回作らない |
| D04 | Policy に Disable を追加する | Immediate / ApprovalRequired / Disable。独立した LendingEnabled は置かない |
| D05 | 申請は非予約 | 申請中は数量を確保せず、貸出成立時に残数を確認する |
| D06 | 今回は承認＝貸出開始 | 承認時に Transaction を作成する |
| D07 | 借り手は User のみ | 所有者は User / Group。OwnerRef は Kind と ID で参照する |
| D08 | 今回は認可を実装せず、全操作・閲覧を許可する | 所有者・管理者・借り手との一致による拒否を行わない。将来の認可方針は別途検討する |
| D09 | PK は (ItemID, OwnerKind, OwnerID) | 同じキーの Ownership は一つ。申請と貸出もこの複合キーで参照する |
| D10 | 全量返却 | 部分返却のモデルを設けない |
| D11 | 貸出中の変更・削除は拒否する方針 | 貸出中数量未満への減数、貸出中・申請中の削除を拒否する。認可とは別の業務制約として扱う |
| D12 | 本・備品の分類と ISBN を削除する | BookDetail / EquipmentDetail は設けない。備品は Group 所有として表す |

認可を全許可にすることは、Policy・数量・状態遷移の制約をなくすことではない。Disable の新規貸出、在庫超過、二重返却などは業務ルールとして拒否する。借り手・操作者の情報はモデルに残す。

## 残る判断事項

- **所有者変更後の履歴参照**：UpdateOwnership で所有者を変更すると複合キーも変わる。過去の申請・貸出の参照をどう保持するか、移転先に同じキーの Ownership がある場合に統合するかは未決。貸出フローの説明を優先し、今回は更新操作の入口とこの注意点だけを記す。
- **Policy 変更時の既存申請**：既存の pending を維持・取消のどちらにするかは未決。通常の貸出フローの説明には影響しないため、変更に伴う遷移は TODO とする。

Like・Comment・Tag・File は現行のモデル・主要操作を維持する。テスト、DB 接続、実行可能性は要求しない。

## 選択

- D01: 貸出のみ
    - このアプリケーションが貸出以外を扱うことはない．所有権移転が必要になるときは，それはUpdateItemとして実装する
- D02: TransactionRequestは分離する
    - Transactionの責務を大きくしすぎない方が適切
- D03: 今回は同じ条件の物品を数量でまとめるとする
    - itemId, ownerIdがPKになるのが望ましい
    - 1つずつ管理する別mockを作るのもあり
- D04: PolicyにDisableを加える
- D05: 非予約
    - 同じitemを複数人が同時に借りることはまれであると考える
- D06: 一旦承認 = 貸出開始とする
- D07: 借り手にGroupは存在しない(Userのみ)
- D08: 提案の通りでよい
- D09: 上の通り (ItemID, OwnerID)をPKとする
- D10: 全量返却とする
- D11: 拒否
- D12: 残さない
    - EquipmentはGroupの所有物とするように設計したため
